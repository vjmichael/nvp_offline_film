# WO5 distribution handoff (source contract, not a release)

Group B Windows native MXF/PCM roundtrip was accepted at `ff0170ec`. The Group C GUI and build staging code are not installed acceptance.

## Host and package layout

- Application: current W1-G per-user NSIS bundle, with its existing recovery and project preservation.
- Native decoder tools: fixed, distinct HKLM Program Files directory `NVP/native-codecs/<independent manifest SHA-256>`, containing exactly five reviewed static codec executables, their complete upstream license notices and canonical manifest. The ordinary application cannot elevate or replace them. No project, PATH, user-local executable or runtime-generated pin may authorize them.
- Production journal: existing host-provisioned EFS `.native-production-runtime` and exact project FilmIndex. No second production owner, arbitrary directory or fallback. The protected-project lock remains in force.
- Build-time: use `tools/nvp_wo5_release_codecs.py stage` with the exact source-reviewed Windows static binaries and complete license notices, then independently freeze resulting manifest hash into `backend/_nvp_wo5_release_pin.py` before building. Audit the complete payload again with `verify --bundle ... --pin ...`. Fixture tests verify hashing and denial, not upstream identity, real license compliance or actual executable behavior. The release owner must separately verify reviewed source revisions, binary hashes and legal notices.
- Installation: the new release-only `provision-machine` command checks an explicitly elevated Windows token, trusted machine owner and non-writable protected ACLs on the fixed Program Files NVP tree, and requires an administrator-prepared, ACL-sealed `NVP/codec-payloads/<pin>` ingress. It copies only the independently verified five executables, notices and manifest to a unique pending directory, checks bytes/ACLs, and publishes a non-overwriting pin directory. The previous pin remains intact and a pending directory is never admitted. The unprivileged installed viewer will verify that exact independent pin, not any alternate runtime folder. Only these public approved codec files have read/execute access for the Windows All Application Packages SID; parent directories have traverse-only access. The zero-capability AppContainer still receives only its unique package SID's private disposable EFS job directory. The installed codec path is separately admitted at the actual launch boundary, never mutates machine code ACLs during playback, and retains original Job/process journals. Developer fixture paths retain the existing per-session code ACL route. The current per-user NSIS script cannot write Program Files. The final canonical release must supply the machine-authorized ingress and include the provisioner from a trusted administrative deployment location with no overwriting of active workers, no symlink/reparse traversal, exact pinned payload verification, rollback and uninstall policy. A codec bundle copied to the per-user NVP directory must not activate the viewer. Do not generate an independent interim installer or weaken the Program Files gate.

## Acceptance still required

Actual protected project and installed native production service/SCM admission; the existing journal reconnect now uses a real read-only SQLite URI with no schema migration or production ownership; active session origin and project revocation; real UI controls and audio-device clock across seeks/reels; source/final read-only identities; abort and recovery; reviewed native payload placement and installed immutable pin; actual creator viewing on Windows. Test fixture or clock scheduling alone is not a sustained 24fps, physical screening, artistic approval, or formal DCI certification.

The compiled pin intentionally remains blank until the final approved build. Do not build a new NSIS installer until consolidated engineering tasks are complete.


## Canonical release source integration

1. Stage the five static reviewed tools and complete notices with `tools.nvp_wo5_release_codecs stage`. Review the resulting manifest independently, then use `bind-release --bundle <approved-payload> --approved-pin <SHA> --pin-module <trusted-build-pin-module>` before freezing NVP. Stage no longer writes a release pin without a separate explicit approval.
2. The final offline release contains one ordinary per-user NSIS application installer and the separately reviewed machine codec payload. A trusted administrator, executing the release provisioner from an independently reviewed administrative deployment location, runs `python -m backend.nvp_wo5_codec_provision --deploy-approved-payload --payload <absolute-reviewed-payload> --approved-pin <independent-SHA>`. This creates protected machine ingress and immutable pinned release; no payload executable is run by the deployment tool.
3. Build the ordinary application package with `NVP_WO5_RELEASE_PIN` and `NVP_WO5_MACHINE_PAYLOAD` set together. The build-side contract checks the literal source pin, complete approved codec payload and absence of codec files in the per-user app. On Windows the staged **actual frozen application** must pass its read-only `--verify-wo5-installer-pin` gate (exact compiled pin and machine ACL/content check) before NSIS writes the ownership marker or promotes the candidate. An unpinned alpha build also checks its actual pin is blank. Missing or mismatched machine files abort and preserve the original install.
4. The user application never elevates or invokes a machine installer, and a per-user uninstall never deletes shared machine codec releases. Existing pins stay intact for active older apps or rollback. Administrative preparation is an explicit separate prerequisite, not a claim of a one-click codec-enabled setup or physical Windows execution acceptance.

No NSIS build is authorized by this source change. The current independent release pin remains blank and real reviewed payload/Windows deployment and service acceptance remain mandatory.

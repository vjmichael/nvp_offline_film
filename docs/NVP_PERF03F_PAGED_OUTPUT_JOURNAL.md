## Durable source and output storage

New submissions through the existing FeatureJournal persist immutable source rows in the same protected SQLite WAL/FULL journal. Additive table production_feature_pages uses feature identity, source/output kind and ordinal primary key. Each page contains 1–64 entries and at most 256 KiB of canonical bytes. Bind ordered page SHA-256 digests and counts into a compact root. Critically, stream the original canonical v1 manifest hash over the original three parallel arrays and header, comparing with the original exact creator-approved manifest SHA, rather than replacing approval with a self-declared page root. Browse reconstructs at most the selected 64 rows, independently verifies the entire canonical digest and page chain in one read snapshot, and never uses browse as a worker grant. Legacy whole-manifest jobs remain readable; no destructive rewrite. New source row and pages commit together after original creator decision. Existing bounded finite publisher still receives the original materialized, exact validated v1 view. This intentionally does NOT remove its existing min(288 reels, FilmIndex MAX_DEPENDENCIES-1) ceiling, or change the XML/package/codec limits.

On native commit, independently verify the exact expected output name universe, refuse linked or nonregular entries before hashing, reopen original source and original DCP structural checks, retain actual source-track binding. Store ordered output file SHA pairs and compact digest pointer atomically with PUBLISHED_PENDING_INDEX. Existing explicit orphan review uses the same receipt storage after its unchanged full media and creator approval checks. Final indexing/publication boundary remains separate. Output checkpoint page chain, canonical file-digest and original approved source SHA binding are verified before read and restart; existing original package re-audit compares actual file and source bytes, not just page hashes. This is integrity evidence inside the original OS-protected journal trust model, not a signed third-party attestation or proof against an attacker controlling the whole database.

## Native custody and restart

One original OS singleton and FeatureJournal transaction. Verify the claimed feature manifest and pages inside the same claim transaction. Refuse other verification, picture, sound/delivery or pending feature index claims while any feature is STAGING. No new worker kind, process, privilege, no FFmpeg. Keep existing finite one-owner publication, scope and approval checks. Recheck exact feature snapshot inside terminal commit/adoption transaction. Restart iterates feature IDs by bounded 64-row keyset batches, checks all jobs, reports only first 64 with exact total and truncation. Damaged manifest enters REVIEW_REQUIRED; interrupted or artifact-bearing work is not automatically requeued. Clean queued cancellation may finalize CANCELLED; staged/target artifacts are preserved and require review even after a cancellation request. Uncancelled complete orphan adoption still requires explicit original consent. No deletion, overwrite, implicit replay or certified acceptance.
